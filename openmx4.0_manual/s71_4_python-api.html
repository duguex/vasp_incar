71.4 Using the API from Python

When using the API from Python, make pyapi generates the Python extension module pyopenmx_api*.so.
The Python-side call has the form

   ierr = pyopenmx_api.run(subcomm.py2f(), input_file, nth)

Here subcomm.py2f() converts a communicator created by mpi4py into a Fortran integer handle. Therefore, to use the Python version, at least mpi4py and pyopenmx_api*.so are required. Note that the Python version is more environment-dependent than the C/Fortran versions. This is because pyopenmx_api*.so is not a mere Python script but a shared object linked to the OpenMX core, MPI, BLAS/ScaLAPACK/BLACS, the Fortran runtime, and Python itself. For this reason, problems may arise not only at build time but also already at the stage of import pyopenmx_api.

Initial build

In the pyapi target, OpenMX object files must be rebuilt with -fPIC in order to create the Python shared object. Object files already produced in a normal OpenMX build may not have been compiled with -fPIC. Therefore, when building the Python API for the first time, execute make clean once and then run make pyapi.

   cd source
   make clean
   make pyapi

This make clean is needed in order to remove existing non-PIC object files and force regeneration of object files compiled with -fPIC. Since the pyapi target itself does not include clean, for the sake of later trial and error, this point should be kept in mind.

Where to modify the makefile

When building the Python version, the part that users should check in source/makefile is the following Python API section. First, as the common part, there are rules that generate the PIC library and pyopenmx_api.o.

   # Common part for OpenMX API for Python with mpi4py

   PIC_API_LIB  = libopenmx_api_pic.a
   PIC_API_OBJS = $(filter-out openmx.o,$(OBJS)) openmx_api.o

   $(PIC_API_LIB): $(PIC_API_OBJS)
      rm -f $(PIC_API_LIB)
      ar rcs $(PIC_API_LIB) $(PIC_API_OBJS)

   pyopenmx_api.o: pyopenmx_api.c
      $(API_CC) -fPIC ‘python3-config --includes‘ -c pyopenmx_api.c

Next, check the definition of the pyapi target. In the distributed makefile, case A is the default setting. In case A, the usual LIB used for linking OpenMX itself is reused as it is to create the shared object.

   # case A for OpenMX API for Python with mpi4py

   pyapi:
      $(MAKE) CC=’$(API_CC) -fPIC’ FC=’$(API_FC) -fPIC’ $(PIC_API_LIB)
      $(MAKE) CC=’$(API_CC) -fPIC’ pyopenmx_api.o
      $(API_FC) -shared -fPIC \
            pyopenmx_api.o ./$(PIC_API_LIB) $(LIB) \
            -o pyopenmx_api‘python3-config --extension-suffix‘

One should first try make pyapi using this case A. Depending on the environment, this alone may successfully generate pyopenmx_api*.so.

If case A does not work, then try case B. In case B, the library group used for linking the Python module is given explicitly as PYLIB. For example, in an environment using OpenMPI and MKL, it may take the following form.

   # case B for OpenMX API for Python with mpi4py

   PYLIB = -Wl,--start-group \
          ${MKLROOT}/lib/intel64/libmkl_scalapack_lp64.a \
          ${MKLROOT}/lib/intel64/libmkl_intel_lp64.a \
          ${MKLROOT}/lib/intel64/libmkl_intel_thread.a \
          ${MKLROOT}/lib/intel64/libmkl_core.a \
          ${MKLROOT}/lib/intel64/libmkl_blacs_openmpi_lp64.a \
          -Wl,--end-group \
          -lmpi_usempif08 -lmpi_usempi_ignore_tkr -lmpi_mpifh \
          -lifcore -liomp5 -lpthread -lm -ldl

   pyapi:
      $(MAKE) CC=’$(API_CC) -fPIC’ FC=’$(API_FC) -fPIC’ $(PIC_API_LIB)
      $(MAKE) CC=’$(API_CC) -fPIC’ pyopenmx_api.o
      $(API_CC) -fPIC -shared \
            pyopenmx_api.o ./$(PIC_API_LIB) $(PYLIB) \
            -o pyopenmx_api‘python3-config --extension-suffix‘

Case B can be effective in environments where case A fails when linking the shared object. However, the contents of PYLIB are environment-dependent. They should be adjusted according to the MPI implementation, the BLACS library name, the Fortran runtime, and so on. Therefore, one should first try case A, and switch to case B only if case A does not work.

Usual execution procedure

What make pyapi generates is only pyopenmx_api*.so.

example_openmx_api.py is a separate file. Therefore, when trying the supplied Python example, copy both the script and the shared object into work.

   cd ../work
   cp ../source/example_openmx_api.py .
   cp ../source/pyopenmx_api*.so .
   mpirun -np 4 python3 example_openmx_api.py

In this Python example, MPI_COMM_WORLD is split into two subcommunicators, and Methane.dat is executed on one side while Cdia.dat is executed on the other. Therefore, at least two MPI processes are required. The number of OpenMP threads is specified not on the execution command line but by nth in the source code. In the example, nth = 1, so the above execution example runs with one thread. If one wishes to change the value, modify nth and rerun the example. In the Python case as well, the same C API is eventually called through pyopenmx_api.run(..., nth), so the maximum number of usable threads depends on the OpenMP runtime environment and the CPU resources assigned at job submission.

The full text of example_openmx_api.py is shown below.

   from mpi4py import MPI
   import pyopenmx_api

   comm = MPI.COMM_WORLD
   world_rank = comm.Get_rank()
   world_size = comm.Get_size()

   nsplit = 2
   nth = 1

   if nsplit > world_size:
       if world_rank == 0:
           print("Error: nsplit is larger than world_size")
       raise SystemExit(1)

   color = (world_rank * nsplit) // world_size
   subcomm = comm.Split(color, world_rank)

   if color == 0:
       input_file = "./Methane.dat"
   else:
       input_file = "./Cdia.dat"

   print(
       "before run:",
       "world_rank =", world_rank,
       "world_size =", world_size,
       "color =", color,
       "sub_rank =", subcomm.Get_rank(),
       "sub_size =", subcomm.Get_size(),
       "input =", input_file
   )

   ierr = pyopenmx_api.run(subcomm.py2f(), input_file, nth)

   print(
       "after run:",
       "world_rank =", world_rank,
       "color =", color,
       "ierr =", ierr
   )

In the Python version, the communicator is split using mpi4py, converted into a Fortran integer handle by subcomm.py2f(), and then passed in the form

   pyopenmx_api.run(subcomm.py2f(), input_file, nth)

On the C side, this handle is converted into a C communicator by MPI_Comm_f2c() and is then finally passed to openmx_api().

Troubleshooting hints

  • •

    If /bin/sh: python3-config: command not found is shown, then python3-config may not be in the PATH, or the Python development package may not be installed. Depending on the environment, it may also appear under another name such as python3.7-config or python3.11-config.

  • •

    The error Python.h: No such file or work means that the Python development header could not be found. This can happen when python3-config --includes fails, and it can also happen when the development package itself is not installed.

  • •

    If make pyapi fails in case A, switch the pyapi target in source/makefile to case B and try again. At that time, confirm that PYLIB is consistent with the current MPI, BLAS/ScaLAPACK/BLACS, and Fortran runtime environment.

  • •

    If a shared-library-related error appears already at the stage of import pyopenmx_api, confirm whether the generated pyopenmx_api*.so is binary-compatible with the Python currently in use, and whether the required MPI/MKL/Fortran runtime libraries can be found at execution time.
    ldd pyopenmx_api*.so is useful for checking such dependencies.

  • •

    Even if mpi4py itself can be imported, incorrect behavior or an abort immediately after startup can occur if the MPI implementation used when building OpenMX differs from the MPI implementation to which mpi4py is internally linked on the Python side. Confirm that the OpenMX build, mpirun/mpiexec, and mpi4py all refer to the same MPI environment.

When users write their own Python script, the simplest approach is to place pyopenmx_api*.so in the same directory as that script. Alternatively, it may be placed in any directory that Python can search.
